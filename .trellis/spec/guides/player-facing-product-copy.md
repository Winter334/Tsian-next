# 玩家可见产品文案指南

> **Purpose**：写或审查 UI 文案时，只向用户呈现完成当前任务所需的信息，避免把开发决策、实现机制和内部流程写进产品界面。

## 适用范围

在新增或修改以下内容前使用本指南：

- 页面标题、说明、按钮、选项卡片；
- 加载、空状态、错误、确认和恢复提示；
- 面向玩家或普通用户的功能名称与帮助文字。

AI-facing 的 Skill、AGENT.md 和工具 description 使用[提示词自包含与口吻指南](./prompt-self-contained-and-tone.md)，不使用本指南替代。

## 受众边界

玩家可见文案只应帮助用户理解四件事：

1. 当前是什么；
2. 现在可以做什么；
3. 系统处于什么状态；
4. 操作会产生什么重要结果或风险。

如果一句话只解释“为什么开发成这样”“旧方案是什么”“内部下一步如何处理”，而不改变用户的理解或行动，就不应出现在 UI 中。

## 不应写入界面的内容

- 采用当前方案的开发决策或原因；
- 已移除、已替代方案的历史对比；
- 用户无法观察或控制的内部阶段与后续处理；
- 组件、数据结构、API、Agent 执行方式等实现机制；
- 不帮助用户行动、判断状态或规避风险的技术术语。

## 写前检查

- [ ] 这条信息会改变用户现在的选择或操作吗？
- [ ] 它描述的是用户可观察的结果，而不是组件、Agent、Schema、表单或内部阶段吗？
- [ ] 删除开发背景和历史方案后，句子仍然成立吗？
- [ ] 它是稳定的产品事实，而不是会随内部实现调整而失效的流程说明吗？
- [ ] 文案只承诺当前功能真实提供的行为吗？
- [ ] 标题、说明和按钮是否各自承担不同信息，没有重复描述页面布局？
- [ ] 用户不需要知道实现方式时，是否已经删掉“通过……实现”“后续将……”等解释？

## 允许解释机制的情况

当机制会直接影响以下事项时，应给出必要说明：

- 等待时间或费用；
- 不可逆结果或数据丢失；
- 权限、隐私或安全；
- 失败后的恢复方式；
- 用户必须满足的输入约束。

仍应优先描述用户结果。例如写“重新导入会替换当前章节”，不要写“系统会重建章节索引并覆盖 manifest”。

## 正反例

### 选择说明

错误：

> 这里只决定角色类型。具体人物、身份和本局偏好会在接下来的对话里逐步确认。

正确：

> 选择使用小说中的已有角色，或创建一个原创角色。

### 实现方式

错误：

> 通过简短问答创建角色，不需要预先填写完整表单。

正确：

> 创建一个新的原创角色。

### 必要风险

错误：

> 系统会清空旧 source manifest 并重新执行导入流水线。

正确：

> 重新导入会替换当前已导入的小说内容。

## 审查原则

不要通过全仓禁词或机械删除来执行本指南。同一个技术词在调试工具中可能合理，在玩家界面中可能不合理；应以受众、当前任务和可操作性判断。发现问题时只修正已纳入任务范围的界面，除非任务明确要求扩大审计。
