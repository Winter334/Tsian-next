# AIRP 数据与能力设计原则

> **Purpose**: 泛用方法论，指导 AIRP 运行时中数据结构、schema 字段、能力归属与写入策略的设计决策。覆盖 agent/skill/tool 能力设计、数据权威与派生、分片策略、字段消费者验证、写入策略、文档分层。刻意保持不绑特定玩法——离开具体场景仍可套用。每条含"原则 + 可操作判据 + 执行手段"。

---

## 何时使用本指南

- 设计新 agent / skill / tool 能力，或决定某能力放平台还是 skill/workspace。
- 设计或修改 entity / runtime / scene 等 schema，新增或移除字段。
- 决定数据放哪、引用怎么表达、聚合层要不要加、同一信息是否需要第二份。
- 决定写入策略（replace vs edit）、文档分层（常驻 vs 按需）、一次性产物落点。
- 审查现有设计是否过度——追问每个字段/能力/文件的真实消费者。
- 验证渐进重构产出时发现可疑设计，需要判断该保留还是移除。

## 原则 1：按频率 × 后果给能力

**原则**：能力供给按"操作频率 × 做错后果"四象限分级。该慷慨时绝不吝啬，该锁死时绝不放任。

**判据**：
- 高频 × 可自纠 → 平台 primitive，不限量供给
- 高频 × 破坏性 → 必须有硬边界工具，且优化往返成本（批量封装）
- 低频 × 破坏性 → 硬边界工具，可接受多步
- 低频 × 可自纠 → 平台 primitive，不专门设计

**执行手段**：
- "慷慨给"：不设人为配额、失败返回可操作错误让 agent 修正重试。
- "锁死"：工具白名单 + 拒绝越界操作 + 平台不暴露不该暴露的能力。

## 原则 2：能力归属由"会不会变"决定

**原则**：一个能力（校验、执行、约定）放平台代码还是放可编辑层（skill / workspace / 卡定义），判据是这条规则会不会因玩法或数据结构变化而变。

**判据**：会变 → 可编辑层；不变 → 平台代码。"重要"不决定归属：重要但稳定归平台，重要但易变归可编辑层。

**执行手段**：把易变逻辑硬编码进平台、或把稳定逻辑散到 skill，都是错配。校验逻辑随 schema 演进 → 放 skill。

**实例：前端编排不硬编码 agent 名**（2026-07-04，`novel-frontend-stage-manager-after-turn`）。Agent 显示名和运行时入口会因卡模板调整而变（改名、换阵容），属于"会变"层。前端调用 agent 必须从卡配置 `runtime.entrypoints` 读 agent id（`tsian.card.entrypoints()`），不写死 `"stage-manager"` 之类的字面量。更进一步的约定：**UI 文案不引用 agent 名**——Toast 只描述阶段行为（"本回合整理中"），不出现 agent displayName。你不展示的东西就无法硬编码：agent 改名只动卡模板，前端零改动。

## 原则 3：是否封装 skill 看往返次数

**原则**：要不要为某操作专门做 skill，判据是裸用平台工具会触发几次模型往返。

**判据**：一次能完成 → 平台 primitive，别包；多次往返（批量取、嵌套展开、分片聚合、多步归一）→ skill 封装一次返回。

**执行手段**：不因"听起来更高层"就封装，也不因"觉得简单"就裸用——看实际往返次数这个客观量。封装代价是多一层维护，收益是省上下文与 token。

---

## 原则 4：两份相同数据必写权威与派生

**原则**：任何时候同一信息存在两处（缓存、索引、快照、聚合视图、冗余字段），必须明确哪处权威、哪处派生、派生如何刷新，并写进该数据层的说明。

**判据**：发现同一信息要写进第二个位置 → 立刻定义主从关系和刷新时机，否则不要写第二份。

**执行手段**：没有写明归属的两份相同数据迟早不一致。权威一处、派生可重建、刷新时机明确。

## 原则 5：会无界增长的量一开始就按自然单元分片

**原则**：某个数据量会不会随交互次数不断增长？会 → 从一开始按该数据的自然单元分片（一单元一文件），不要单文件累积到瓶颈再拆。

**判据**：问"会不会无界增长"，不是"现在大不大"。现在小但会涨 → 一开始就分片；现在大但恒定 → 单文件可。分片单元选该数据自身的自然边界（一个主体、一个会话、一个时段），不按技术规则硬切。

**执行手段**：拖延"以后再拆"只会让拆分更痛，且拆分前已造成检索瓶颈。

---

## 原则 6：一次性产物必落到后续能读到的路径

**原则**：初始化、导入、一次性生成类流程的产物，落点必须满足"后续常态流程的 agent 或前端能从既有路径读到"。

**判据**：这个产物生成后，常态运行时谁还会读它、从哪读？答不上来就不要落盘，或改落到既有路径。

**执行手段**：绝不允许写进只有这一次流程自己消费的孤儿路径。一次性消费的内容留在内存或临时区。

## 原则 7：写入策略按客观状态决定

**原则**：replace 还是 edit、整文件还是局部，按"当前文件实际大小 + 本次改动占比"自适应，不按"这类文件该用这种模式"预设。

**判据**：旧内容 > 阈值 且 改动 < 比例 → edit；否则 replace。客观量（长度、比例）决定，不是主观分类。调用方可显式覆盖。

**执行手段**：给合理默认阈值（如旧内容 > 2000 字符 且改动 < 30% 用 edit），不按文件类型贴标签。

---

## 原则 8：文档分层按读取频率

**原则**：一份规范文档进不进常驻上下文、写多详尽，判据是谁、多久读一次。

**判据**：
- 每次操作都查 → 进常驻上下文，且保持精简
- 偶尔查 → 按需读取，可以详尽
- 一次性流程 → 随该流程的 Skill 按需加载，不常驻
- 开发者方向 → docs/active，agent 不读

**执行手段**：高频常驻必须精简（否则污染每次上下文），低频按需可以详尽（反正不常占位）。判据是读取频率，不是"内容重不重要"或"详不详细"。

## 原则 9：每个字段必须有一个真实消费者

**原则**：schema 里的每个字段、entity 的每个属性，必须有一个明确的消费者——某个 Agent、前端或工具会读它，并且读后能做出一个具体的、与不读时不同的决策。没有消费者的字段就是过度设计，不论它"听起来多合理"。

**判据**：对每个字段追问三步：
1. **谁读它？** 指出具体的消费者（Agent / 前端 / 工具），不是"可能有人用"。
2. **读了做什么决策？** 读后行为与不读时有何不同？如果行为不变，字段无价值。
3. **删掉会怎样？** 如果删掉后没有任何 Agent 行为变、没有前端展示变、没有工具输出变——它就是冗余，应该删。

**执行手段**：
- 不要为字段的功能性辩护（"能追溯""能标记""能索引"），要从消费端验证它是否有真实消费者。
- 警惕三类伪消费者：
  - **审计字段**（`updatedAt`/`updatedBy`）：来自传统 DB 思维，但 AIRP 单写入者、turn 顺序执行，无并发冲突，无审计消费者。
  - **冗余索引**（`sourceRefs`）：试图在 entity 里存源文本指针，但 source 本身可搜索、semantic_search 更精准、frontier 记抽取进度——被 better 工具替代。
  - **约束标记**（`origin` 的部分语义）：约束已隐含在方法论原则里（spoiler-safe、只读已读内容），再加标记字段是重复表达同一约束。
- 发现无消费者字段时直接删，不要"降级保留"或"改成可选"——降级保留是最差状态，既不消费又要维护。

**实例：entity 审计字段移除**（2026-07-07，验证 Understanding 步产出后发现）。`updatedAt`/`updatedBy` 在 entity 里无消费者：Agent 决策不读它、前端不展示它、调试有 runtime trace 更精确。开局实体强制写入这两个字段是 `commit-entities` 脚本从传统 DB 思维带过来的残留。同理 `sourceRefs` 试图在 entity 里冗余源文本索引，但 source 可搜索 + semantic_search 已覆盖溯源需求。两者都应移除。

## 原则 10：卡内分发源是 AI 能力的验证边界

**原则**：游戏卡内的 `workspace/` 与前端入口才是实际维护和分发源；平台 workspace template 停止维护后，不为卡内能力改动同步修改模板。

**判据**：改动 agent、skill、workspace tool 或卡内编排时，只检查对应卡目录及其打包流程；只有明确要求恢复模板维护时，才触碰平台模板。

**执行手段**：以卡打包产物作为 AI-facing 能力的最终边界，确认产物包含卡内指令与工具，并排除 `save/` 等运行时目录。这样可以避免修改无实际消费者的模板副本，也避免“源码改了但分发包没带上”的错觉。
