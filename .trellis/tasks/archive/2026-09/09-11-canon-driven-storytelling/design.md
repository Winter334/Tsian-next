# 设计决定与实现约束

## 当前方向为何改变

此前的语义化消除了不少文件维护负担，但仍是“架构师读原著并预建资料 → 写手根据资料重新创作”。用户实测认为，原著人物、因果和文风的损失，比隔绝原剧情所带来的防剧透收益更大。现在让创作者直接掌握原著，由场记整理创作结果。

参照关系：原著提供世界/前史和默认走向；本局已落定事实维持连续性；玩家输入导致新的行动与后果。原著未来不是本局已发生事实，也不是故事必须重新并回的轨道。

## 已确定与不要再提的替代方案

| 议题 | 最终决定 | 不采用 |
| --- | --- | --- |
| 正文与原著 | 写手有相关原文和阅读能力，结合本局自然续写 | 只注入实体摘要、限制作者不准了解必要剧情 |
| 防剧透/全知 | 约束角色认知、叙述视角与揭示时机 | 为此建立逐角色知识库/复杂读取锁 |
| 酒馆移植预设 | 先主推原著文风，低成本沿用，否则停用 | 全面重建通用预设系统，逐模块强行兼容 |
| 输入“继续” | 与其他输入一样基于上下文续写 | 特判、强制回原著、额外重大决定确认机制 |
| 实体建立 | 场记统一建立并维护本局已确认资料 | 架构师先生成完整可渲染对象库才能开写 |
| 实体身份 | 内部稳定 ID，外部名称/别名查询与候选确认 | 名称作为唯一 ID、按同名静默合并 |
| 时间线 | 本局已发生的重要历史记录 | 原著未来图、分支对照/偏离/并回展示 |
| 写手大纲 | 有需要才保留短期创作意图，随剧情可改 | 每轮先写大纲、固定规划调用、计划当历史 |
| 原著差异 | **整项取消识别与展示** | 场记读原著对比；让写手提交差异报告 |

最后一项是用户最新纠正：此前曾考虑“场记对照原著标偏离”，随后因维护成本不值而明确取消。不要从本会话中间建议或旧任务复活该功能。

## 建议的最小闭环

1. 保留选书、角色/切入点和方案显式确认的用户体验；剧情访谈由写手承担。
2. 架构师根据作品做必要的世界概念/规则/展示适配，专用工具完成程序存储，不预建人物库存。
3. 写手拿到确认方案、相关原文与必要世界规则，生成开局；正文独立持久保存。
4. 场记拿到正文和确认前提，首次建立实体、场景、关系与当前状态，提交凭据通过才允许进入故事。
5. 后续继续使用“写手阅读/续写 → 场记整理”的闭环。世界适配不是固定的逐轮调用。

这是职责顺序，不是要求新建通用工作流引擎。UI/文件/动作的具体拆分由实现者按现有卡结构收敛；不要要求用户确认字段形状。若确需扩大产品范围再询问。

## 原著材料与文风

- 优先复用现有 source manifest/index/shard 读取实现，把对写手有用的阅读和定位封装为专用能力。返回实际内容、章节标题/范围和截断信息；不让模型拼路径。
- 卡属上下文应保证当前创作有可用原文/剧情依据，不只摆出一个工具名却继续仅注入资料摘要。可组合必要片段的程序准备与按需补读，不要求整本注入。
- 当前“原作文风”不是成品风格，而是要求按 frontier.sourceWindow 学习并回写模块的旧指令；必须一起处理。
- 通用写作限制可能把原著情绪/对白统一改成克制内省。审视实际启用的材料，保留工具/输出协议等必要部分，冲突者停用或最小改写。无需逐个旧模块做兼容层。
- 作者获得的未来信息不能自然变成角色已知信息或前端公开大纲。可变创作笔记只服务续写，不由场记落实成未发生事实。

## 场记初始化与查询

- 当前初始 runtime 模板已有空指针；当前维护代码仍假设已有可读 runtime/相关实体。需要验证无预建实体情况下，turn 0 首次整理能建立主角、场景、位置等，并以生成后的引用刷新 runtime。
- 玩家确认的必要前提可以进入首次维护，不等于让场记阅读整段原著或判断原著差异。
- 正常更新中保留已有语义维护类别和提交凭据。不为这个任务同时重构记忆分类。
- 查询候选可以先按名称/别名等确定性条件收敛，Agent 用语义资料判断身份。未注入不等于不存在；查询结果截断不等于不存在。
- 创建检查应由程序兜底，不能只给提示词加“记得先查”。但真实同名对象仍须有明确区分后合法新建的路径，不把同名视为绝对唯一性约束。
- 查询/去重只做本任务所需最小机制，不引入向量检索、RAG 或万能实体消歧框架。

## 历史时间线与旧字段

新的时间线消费者从已落定正文、场记现有记录/摘要中取得历史节点；重要程度是语义判断，不要求每轮新建“里程碑”。内部 ID/回合定位可由程序处理。

清点旧 useFrontier/TimelineGraph、上下文的 source 节点、stage-manager milestones/plotOrder 对齐要求等直接消费者并一致调整。不要造空 frontier 文件来掩盖 UI 错误，或保留旧字段假装系统仍推进。

本轮不是宣称所有机器字段无用；也不是把 plotOrder 因为是数字就称为机械字段。只退出已经明确取消的职责及其无用依赖，原文阅读定位另按需要最小表达。

## 沿用而非推倒的底座

- Agent 交付语义，程序处理存储/引用；卡属 schema 可变，通用注入器不理解 schema。
- 固定的非语义后续调用由卡前端编排，不还给架构师 agent_call。
- 每次 invocation 独立提交，responseRef 不能跨调用复用。
- 已实现的独立正文 transcript 保存平台投影结果，可避免 UI 响应丢失后重写正文；继续保留这一价值，按新闭环更新原 model/phase 前提。
- Frontend Action 保留原子发布/完成，场记提交核验之后才成功；刷新恢复不能静默新增模型调用。
- initial-save 跟随卡；只维护 workspace 与真实卡前端的权威源，分发走真实卡包。


## 落地决定（2026-09-11）

- 不新增平台协议。原著阅读放在卡共享 `skills/原著阅读/`，写手和架构师显式启用；访谈是写手本地 Skill。Agent-local Skill 不能靠另一个 Agent 的 enabled 路径变成共享能力。
- 程序预注入书签附近的连续原文（默认 8,000 字符），Skill 支持任意章节/章内偏移、关键词定位、分页续读和显式 remember。单次至多 12,000 字符/20 个章节片段，返回实际位置与 next；章内偏移按 UTF-16，不清洗原文后再计算偏移。书签不推进 runtime，架构师不更新写手书签。
- 初始开局 `model` 字段名沿用，意义缩小为世界/schema 适配的文件签名与提交 ID；只管理 world.json/current.md/setup-summary.json。独立正文 slot、发布 Action、凭据与 checkpoint 沿用，不为改名重建工作流。
- 场记首次建档支持 world.protagonist 和同批 @key 引用；程序核验主角、地点、活跃场景互相一致。人物的已确认阶梯/同阶评价可转换成安全整数属性，装备槽与贡献仍由程序计算；没有依据的值可不填。
- 创建保护采用完整分页枚举和规范化名称/别名相交，不做向量检索或自动合并。冲突时返回首个未解决对象的候选及 remainingConflicts，整批没有业务写入。真实同名对象必须列全 distinctFrom 与区别原因；同批新对象也参与检查。lookup 返回全局名称检索完成标志与结果页游标，改名保留旧名。
- 重要历史用 `recall.important` 翻译为既有 turn.meta.recall 的“重要节点”，展示直接复用“摘要”。取消 milestones、plotOrder 与源节点注入，不新增第二份完整剧情摘要。
- 默认仅启用快捷回复和原作文风，保留真实宏引用；停用预填承诺、统一人称和额外 NSFW Skill 等与当前闭环不必要的约束。不改通用预设框架，不为“继续”增加流程。


## 0.3.1 实测修正

用户已确认属性允许“统一基准＋有限推断”的游戏化估值，不再因没有精确原文数字而让已定义维度空缺；估计不能冒充原著事实。保留既有数值及训练变化，不每轮重估；程序不能把缺层级当最低层级。角色标题不再回退完整简介。具体落地、数值增量与 UI 规则及证据见 [follow-up.md](./follow-up.md)，以此补充上面初版的“未知数值可不填”口径。
