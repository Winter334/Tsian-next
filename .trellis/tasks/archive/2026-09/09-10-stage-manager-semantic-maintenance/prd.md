## 背景与用户意图

起点是用户提供的 `tmp/正文后处理请求.json`：玩家第 2 回合诊脉结束后，场记加载维护 Skill、读取人物/场景/关系/进度、编辑多个文件，再维护 memory 与 recall。用户并非要求继续做请求耗时或任务量分析，而是质疑为什么剧情资料更新需要 Agent 理解存档系统。

用户确认的方向：正文 Agent 根据上下文、相关资料和玩家输入续写剧情；场记根据已落定剧情更新资料；世界架构师生产资料并维护概念/schema。各 Agent 应通过专用工具处理其职责内容，不承担文件系统、引用同步和存储格式维护。现有 schema 很大一部分服务前端渲染，不应因此要求 Agent 理解整个系统。

## 已确认的边界

1. 场记做“结合已有状态的语义增量提取”，而非脱离旧状态摘抄正文。
2. Agent 判断事实、当前状态、意图、人物认知、关系变化、长期影响；程序负责路径、结构包装、编号、引用一致性、确定性投影、保存和刷新。
3. 按是否需要剧情判断划分职责，不按数字/文本分类。`plotOrder` 需要判断当前剧情到达哪个原著节点，明确属于语义信息，不能与机械回合计数一起删除或自动加一。
4. `turn`/`updatedAtTurn` 等执行信息不属于场记的资料维护责任。当前消费者即使存在，也只是迁移时要处理的依赖，不是让场记继续读写它们的理由。无真实用途者删除；必要者由程序管理。
5. 场记由直接编辑文件转为提交语义变更。只改提示词、只改 Skill 或只改工具均不够，必须同步调整输入、指令、协议、执行脚本和结果反馈。
6. 通用上下文注入器保持 schema 无关。修改的是场记的注入配置与注入源文件；如需准备动态语义材料，由卡内配套逻辑产生，不让通用注入器解析玩法 schema，也不影响其他 Agent 的注入语义。
7. 底层文件可以继续混存语义字段和机器字段；模型的读写接口与底层文件不必同形。不要把全库改成纯文本当作转型前提。
8. schema/存档演化要留在卡可编辑能力层。世界架构师可判断概念和展示意图，但物理迁移、引用处理和格式落盘也应由工具承担。

## 范围

- 场记 AGENT/SOUL、回合后维护 Skill、语义读取/提交工具、注入材料与相关生成点。
- 接续现有实体查询、局部更新、recall 工具能力，不把通用 `json_edit` 换个名字就视为转型完成。
- 核对真实前端调用文案、读取/刷新消费者；按前置任务确认的生产源改动。
- 必要的 memory/recall、状态/履历/关系/场景、剧情坐标语义合同。现有资料分类先保留，最终形态由实际测试持续迭代，不在本轮删并记忆体系。
- 用户确认新协议后再决定具体 schema 调整；不是本任务开始就重构全部 Agent。

## 验收方向

- [x] 正常回合中场记不需要文件地图、点路径、存储数组形状、手工记录序号或更新元数据。
- [x] 协议和指令支持根据正文与旧状态提交明确语义变更，区分未知、不确定和意图；工程夹具验证落盘，实际模型判断由用户测试。
- [x] 程序处理格式、标识、引用、确定性派生及必要刷新，并明确报告未应用项。
- [x] `plotOrder` 等语义判断仍可表达；不存在“看到数字便自动管理”的误划分。
- [x] 提示词、Skill、工具、上下文来源和真实消费者一致；以实际打包/导入/Worker 与假 provider 请求验证，不只看仓库源码。
- [x] 人工指定的诊脉变更集正确维护人物、场景、记忆与召回；新履历能被真实正文上下文 formatter 读取。
- [x] 验证重试不会重复计数/追加；已有状态、未知信息和其他 Agent 不被破坏。

## 测试责任与完成边界（2026-09-10 用户确认）

- 真实 AI 调用、叙事事实提取质量、用户体验与资料分类是否合适，由用户在实际游玩中测试；不要求本地配置模型 API 或代用户消耗模型额度。
- Agent 负责方便执行且有必要的工程验证：协议输入/输出、语义投影、脚本变更与引用、校验/失败处理、重复执行、前端编排、必要的构建和卡包验证。
- 可以用用户提供的诊脉正文和人工明确的变更集作为固定测试数据，验证程序如何保存这些变化；不能把这种测试报告为“AI 已能正确提取事实”。
- 工程完成不以真实模型端到端测试通过为前提。交付说明应区分已验证的程序行为与待用户观察的模型行为，并给出精简的实际测试场景。
- 测试服务于本次改动的具体风险，不构建泛用 AI 评测平台、不为未承诺能力做无关大范围测试。
