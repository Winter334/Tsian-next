# 讨论与设计记录

## 1. 语义与机械职责

诊脉样例中，需要模型判断的是：司徒允所说“无病无毒”不等于玄脉修复；“像练了二十年内息”不等于获得二十年修为；诊脉目标已经完成；谁留在场景；疑虑不等于发现秘密。需要旧状态才能判断新增、修订、结束和不变。

不应由模型处理：ref 到路径、关系文件分片、双向关系的物理同步、`history` 的对象包装、记录序号、执行回合元数据、组件刷新信号。同一关系是否双向改变仍是语义判断；只有已经明确的双向写入才由程序执行。不能声称 scene/relationship 名为“派生视图”，现有任意叙事文本就能自动无损生成它们。

当前倾向的交互边界：正文 + 相关语义状态 → 场记提交结构化语义变更 → 程序校验并应用。实体稳定 ID 可保留以消除歧义；无需对模型暴露文件路径、任意 JSON 点路径和全部存档结构。最终工具名、变更种类、部分失败与提交粒度尚未定案。

## 3. 注入器与卡内文件的职责

`apps/platform-web/src/agent-runtime/context.ts` 当前读文件原文并展开宏，无需加入玩法 schema 投影。

讨论中的候选方案是卡内逻辑准备场记专用语义上下文文件，原注入器按路径读取；也可把不适合常驻的信息留在专用读取工具。最终文件名、准备时机、是否采用一个聚合文件仍待设计，不能将候选建议当作用户已批准。

若产生专用上下文文件，它只能是可重建的读取材料，不是另一份要由场记手工同步的权威存档。动态文件需要明确生成时机、新开局/维护重试/回溯后的刷新方式，不能只添加静态 Markdown 名称就认为完成。共享的 `schema/current.md` 明确也被世界架构师使用，应优先更换场记注入来源，避免破坏共享材料。

## 4. 当前工具的连续性

- `query_entities` / `read_entities` 已隐藏部分文件导航，但结果仍泄露完整实体结构/部分元数据。
- `json_edit` / `text_edit` 包装了可靠写入，但仍把字段形状、数组匹配、文件内格式责任交给模型。
- `commit_turn_recall` 更接近领域提交接口：模型给内容，脚本定位、包装、校验。
- 卡目录残留 `read_maintenance_context` 工具，但当前场记未启用；不能将其描述当成运行中能力，也不预先决定恢复旧聚合方案。

## 5. 本轮发现与纠正

- 样例新履历写成字符串数组，而指南规定 `Array<{ event: string }>`。现用 `apps/play-frontend-dev/src/lib/context-injection.ts` 仅读取对象 `event`，跳过字符串；说明文本提取正确也可能因存储格式责任错位而不可消费。此观察是后续验证用例，不在记录任务时顺手修实现。
- 早期分析误以卡目录 `frontend/src` 代表最新消费者，提出 StatusBar 主角刷新依赖 `updatedAtTurn`。已纠正：真实打包前端来源是 `apps/play-frontend-dev/src`；主角 watcher 已用 `runtimeRevision`。仍有部分组件/解析/开局判定引用 `updatedAtTurn`，需按真实调用链分别处理，不能泛称无引用。
- 请求在写完 recall 的工具结果处结束，未包含当前回合最终汇报；前面“回合后维护完成”是上一回合历史。不要误当本回合完整响应或耗时日志。

用户询问还有哪些需要讨论。建议不再重议已确认的职责/plotOrder/通用注入器边界，也不为名称和 JSON 形状逐项请求确认。当前提出以下第一版边界：

2. 场记使用每回合独立的维护上下文，不再依靠跨回合维护聊天历史获取事实。卡内脚本在调用前（含重试）准备可重建语义材料，提供本轮正文、当前局面、必要世界规则和相关资料；其余资料按需查询。该材料不是新增事实权威，也不改通用注入器。是否正式采用无跨回合持久对话的运行方式，等待用户确认。
3. 正常流程以一个语义变更集表达本轮更新，程序先完整校验再应用，避免让场记承担逐文件执行/检查。一次提交不是强制只调用一次模型，仍允许必要查询与修正。失败反馈指向语义对象和原因，不要求模型修复底层文件。提交原子性以当前工具/工作区事务可实际保证的边界实现，不凭空承诺跨系统事务。
4. memory/records、seeds、turn recall 暂不删并；程序承担物理格式和确定性投影，但“是否是长期经历/伏笔、哪些内容值得召回”等仍是模型语义判断，不能把任意文本意义判断藏进脚本。新概念若超出可表达范围，明确报告或交给世界架构师，不恢复场记原生文件编辑作为常规兜底。

## 2026-09-10：实际实现的决策与修正

- 动态材料由实际卡前端生成，普通语义映射通过 workspace 读取卡内 `semantic-fields.json`。不用 `frontend-actions` 共享 helper：gameplay Agent 快照有意隐藏该目录，不应为了复用绕过边界；也不能从分发的 frontend/src 以仓库外相对 import 读取卡源码。
- `lookup` 与 `submit_changes` 都是唯一启用的回合后维护 Skill action。保留资料类别、records/seeds/recall、plotOrder 与玩家显著事件（milestones）；主体/条目标识作为不透明语义指向，物理路径、引用包装、编号、更新时间与装备派生在脚本中完成。
- 复用真实 Skill runner 的 savepoint。脚本先完整校验与暂存业务变更，再写入；runner 在写入失败或输出校验失败时回滚。平台现有 Skill 输入校验仅检查顶层类型，因此卡脚本按自身声明做递归类型/字段/范围校验，不扩大为平台 schema 框架。
- 装备管理 core 保持唯一确定性计算实现。物品转移、容器变化或装备效果变化触发相关装备投影刷新，不让场记提交 applied/expectedCurrentRef 或追查物理拥有者。
- 仅 `persist:false` 仍会通过 runtime fallback 继承游玩历史。新增通用调用选项 `includeRecentHistory`，默认 true，场记显式 false；SDK、remote bridge、host 联动，并用假 provider 捕获请求测试。该变更不改注入器，也不改变其他 Agent 的默认上下文。
- `tools.disabled` 扩展到原生工具名的暴露/直接执行过滤；脚本 SDK 保留受 actor level 与 gameplay workspace 边界约束的原有权限。旧专用 Tools、schema演进检查与 workspace-map 均不再启用/引用；旧文件仍在源树中，但不是当前执行入口。
- 必须核验脚本落盘的回合凭据才能 synced；不接受仅有 completed 事件的成功。已提交后中断可无模型重试；正文变更/旧资料比较基线改变则拒绝，需重新准备或回溯。
- 本轮不搬迁既有平台场景清理逻辑，不重构世界架构师/正文 Agent，不对已有存档自动迁移。实际 AI 效果由用户测试。
