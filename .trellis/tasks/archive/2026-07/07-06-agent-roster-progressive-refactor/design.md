# 素材库模型设计文档

> 本文档记录 2026-07-07 架构讨论的决策推理过程，作为 `07-06-agent-roster-progressive-refactor` 所有子任务的共享设计参考。PRD 记录"做什么"，本文档记录"为什么这么设计、考虑过什么 alternatives、放弃了什么"。

## 1. 起因：验证 Understanding 步产出暴露的问题

`07-06-understanding-step-world-architect-director` 完成后，浏览器验证产出的角色实体和 director brief 时发现两类问题：

### 1.1 entity schema 无消费者字段

验证飞星实体时发现 `updatedAt`/`updatedBy`/`sourceRefs`/`origin` 四个字段无真实消费者。追问三步（谁读它？读了做什么决策？删掉会怎样？）确认：

- `updatedAt`/`updatedBy`：审计字段，DB 思维残留。Agent 决策不读它、前端不展示它、调试有 runtime trace 更精确。额外发现 commit-entities 脚本写 `updatedAt`（ISO 时间戳），schema guide 用 `updatedAtTurn`（回合号），字段名不一致。
- `sourceRefs`：冗余索引。researcher 溯源用 semantic_search 更精准；world-architect 抽取进度靠 frontier；前端不展示。对贯穿全本的主角，列"所有出场章节"会无限膨胀；列"关键事件出处"需要维护 Agent 持续阅读原文判断"关键"——维护成本高且标准模糊。
- `origin`：约束标记。前端用 localId 命名约定（`original-` 前缀）判断分支，不读 entity.origin（grep 零命中）；Agent 用 spoiler-safe 等方法论约束，不读 origin。

思维方法沉淀为 `airp-data-capability-design-principles.md` 原则 9：每个字段必须有一个真实消费者。警惕三类伪消费者：审计字段、冗余索引、约束标记。发现无消费者字段时直接删，不降级保留。

### 1.2 brief 混淆三个读者

验证 director brief 产出时发现它同时写给三个读者：

- 说书人：需要"当前局面有什么可用素材、哪些不能剧透"
- 导演：需要"节奏把控、伏笔进度、何时刷新"
- 场记：需要"什么情况下该标记 brief 过时"

三种需求塞在一个文档里。Skill 定义列的"应包含"内容就是混的——"可用人物场景"给说书人，"何时刷新"给场记，"叙事边界"给说书人，"阶段目标与张力"给导演。

`save/director/README.md` 的设计初衷是"help the storyteller use available material"——给说书人的。但 Skill 和实际产出滑向了"导演工作笔记"。

## 2. 核心转变：原著中心 → 素材库模型

反思 brief 问题时追溯到更深的问题：**原著在 AIRP 里的定位是什么？**

### 2.1 旧模型（原著中心）

- 原著是剧本，要跟着走
- 导演控制剧情方向、节奏、伏笔
- brief 指导创作方向
- "原著/分支平衡"是核心概念

### 2.2 新模型（素材库模型）

- 小说是素材库不是剧本。玩家剧情是主体，原著不一定都用得上。
- 渐进阅读按需取用，不全本理解。
- 说书人用已有素材自由创作，不受预设方向约束。

### 2.3 渐进阅读的意义

为什么不一开始就全文理解？

1. **减少开局等待**：小说往往很长，全文理解需要等待非常长时间。
2. **不提前拿全部素材**：原著的东西不一定都用得上。按需取用避免无用素材。
3. **利用小说的伏笔和长线剧情**：全文理解会提前暴露伏笔和悬念（AI 可能乱用）。渐进阅读让伏笔在被读到时才可用——AIRP 无法像小说那样埋长线伏笔，但可以借用小说已有的安排。

### 2.4 伏笔利用是架构自然发生的

1-20 章的伏笔，说书人随便发挥也不会触及第 50 章的揭晓（信息边界天然隔离）。等提取到第 50 章，看当前剧情：
- 伏笔因为剧情发展被提取解决了（未揭晓就解决了或被说书人以原创内容解释了）→ 忽略相关内容
- 没有解决 → 实现了一次长线伏笔

不强求，这正是 AIRP 的魅力——一切皆有可能。不需要专门的角色管理伏笔。

## 3. 导演移除

### 3.1 导演的三个职责在新模型下都失去依据

- 剧情方向 → 玩家驱动，不需要
- 节奏控制 → 说书人自己把握，不需要外部控制
- 原著/分支平衡 → 不按原著走，没有"平衡"问题
- 伏笔管理 → 伏笔来自素材库（渐进阅读），不是人为设计

导演是"原著中心模型"的产物——当模型变成"素材库 + 玩家驱动"，导演就没有位置了。

### 3.2 brief 移除

brief 的本质是"原著走向指导"。在素材库模型下：
- 玩家剧情是主体，不需要"应该往哪走"的指导
- 小说是素材库不是剧本，没有"原著走向"要遵守
- brief 混淆三个读者的问题无法通过"重新定位"解决——因为它的三个读者需求本就不该塞在一个文档里

timeline 机制替代 brief 的索引功能（见 §5），但不含方向性指导。

## 4. 渐进阅读触发机制

### 4.1 问题：谁决定"该读新章节了"？

讨论了四个方向：

| 方向 | 描述 | 判断 |
| - | - | - |
| A. 说书人触发 | 说书人觉得素材不够时 call researcher | 增加说书人决策负担 |
| B. 场记触发 | 场记检测素材充足度 | 场记承担主观判断，偏离"记录者"定位 |
| C. 前端按客观信号 | 每 N 回合/地点变化 | 太机械，前端不懂剧情判断 |
| D. researcher 按需 | 被调用时查不到就推进 | 最自然，但可能读太多 |

### 4.2 AD 结合方案

researcher 被 call 查素材时：
1. 在已读章节找 → 找到返回
2. 找不到 → 映射 timeline 锚点 → 从锚点 chapter + 10 章窗口找。过去章节不找，窗口外不读。
3. 窗口内未读章节 → 推进 frontier 读 → 找到提取返回，找不到返回无

**关键限制**：不是"找不到就全文搜索"，只在"当前节点 + 窗口"范围内找。窗口外不可读——否则伏笔和悬念提前暴露。

**窗口大小**：固定 10 章。理由：章节号不等于剧情进度，但 10 章作为一个粗粒度窗口够用——太大会暴露伏笔，太小会总是找不到。不需要动态调整。

### 4.3 frontier 推进触发（A' 方案）

**问题**：AD 结合方案中 researcher 找不到时推进 frontier，但这会阻塞调用方（当前 agent_call 串行）。

**讨论的解决方向**：
- A'. 前端在场记完成后检查 worldTime/锚点/sourceWindow 边界 → 接近则前端 invokeAgent("world-architect") 推进
- C. agent_call 支持"先返回再后台继续"——需要平台能力开发

**决策**：走 A'，不改平台。A' 用已有 invokeAgent 机制（独立通道、独立 transaction、不阻塞主回合）。C 暂记，未来如果 A' 时机不够精准再考虑。

**A' 的"接近"判断**：前端做客观计算——`worldTime` 变了？映射的锚点 chapter 接近 `sourceWindow.end`（差 3 章以内）？接近则触发。不依赖 Agent 主观判断。

### 4.4 后台 agent 调用（问题 1，暂不做）

调研了当前 agent_call 机制：
- 纯串行（`index.ts:1184` await 完整 tool loop）
- 同轮多个 agent_call 可并行（Promise.all），但调用方等全部完成
- invokeAgent 有独立通道/transaction，但只能前端发起

异步通知方案（可能 2：完成后注入调用方下一轮）技术上可行但需要平台开发。分两步同步变体（researcher 找不到返回"已触发推进"，下轮再查）更简单——配合 A' 前端触发，完全不需要改 agent_call。

## 5. 时间线方案

### 5.1 问题：怎么判断"当前该读什么"？

方向 D（章节号 + entity）最简洁，但有个漏洞：章节号是原著的线性进度，玩家剧情线可能完全不沿原著走。玩家偏离原著时，按章节号找的素材可能不相关。

### 5.2 剧情节点指标

需要把"玩家当前剧情位置"映射到"原著章节位置"。讨论了：
- 章节号锚点（太粗）
- 章节号 + 已登场角色列表（额外维护成本）
- 事件锚点列表（"关键事件"主观判断）
- 纯章节号 + entity（主角视角外登场的角色不在 entity 里）

### 5.3 手动建立时间线

不追求精确，只求"大致反映原著时间线"。关键洞察：

**时间标记不依赖原著，独立建立。**

- 开局建一个基准（元年），之后所有时间都相对基准推算
- 不从原著提取时间标记（原著时间不稳定、不精确、不统一）
- `runtime.worldTime` 记玩家当前世界时间，场记每回合维护
- timeline 锚点记 `{ chapter, time, label }`，world-architect 渐进补充

### 5.4 时间粒度

- 默认"年+季/月"（如"二年秋"）——大多数时候够用，维护成本低
- 允许场记按剧情需要调整粒度——日常修炼期用季节粒度，紧迫赶路期用日粒度，时间跳跃用相对粒度
- 不固定格式，自由字符串——和 `runtime.worldTime` 一致

### 5.5 timeline 不是 brief 变体

| 维度 | brief | timeline |
| - | - | - |
| 内容 | 剧情方向、节奏控制、伏笔管理 | 章节号 + 时间标记 + 一句话标签 |
| 性质 | 方向性指导 | 客观映射表 |
| 对创作的影响 | 直接约束 | 间接影响（只影响找素材范围） |

**label 约束**：一句话标签，不是剧情摘要。防止滑向 brief。
- ✓ "飞星下山"（标签，客观）
- ✗ "飞星下山，与广刹因灵蛇剑起冲突，导演应控制此段张力"（brief 式指导）

### 5.6 玩家扮演原著主角 vs 原创角色

两种情况下 timeline 机制相同（都是素材索引），只是说书人使用方式不同。不需要在 schema 层面区分。

## 6. Agent 阵容变化

| Agent | 旧职责 | 新职责 |
| - | - | - |
| storyteller | 读 brief 写正文 | 用已有素材自由创作 |
| researcher | 检索已有资料 | 检索 + 映射 timeline 推进 frontier 找新素材 |
| stage-manager | 整理变动 + 检测 brief 刷新 | 整理变动 + 维护 worldTime |
| world-architect | 建模 + 玩法启用 + 被 call 写 brief | 建模 + 推进 frontier 提取素材 + 维护 timeline |
| director | 维护 brief | **移除** |

## 7. 焦点不在原著主线

时间线方案下基本自然解决：
- 玩家偏离原著 → `worldTime` 仍按剧情推进 → 映射 timeline 锚点 → 找素材
- 找到的素材可能不相关 → researcher 返回无或标注无关 → 说书人原创
- 等玩家剧情时间推进到原著相关节点 → 自然又能找到素材

**可接受的浪费**：A' 方案下，玩家偏离时 frontier 推进可能读不相关章节。但推进 ≠ 提取——读到不相关的章节不提取 entity，只消耗 LLM 调用。成本可控。

## 8. 设计原则（讨论确认）

- **AGENT.md**：写定位与方法论，不写具体步骤
- **SOUL.md**：写人格底色，泛化不绑步骤
- **Skill description**：准确精简描述，无额外解释
- **Skill triggers**：使用时机，配合前端 prompt 稳定触发
- **Skill 正文**：需要做什么/怎么做/出问题怎么办，不出现设计决策
- **Tool 判断**：通用复用 → Tool；服务 Skill 流程 → Skill 脚本
- **contextPaths**：高频常驻参考文件，不是职责边界声明，Agent 可灵活直读
- **每个字段必须有一个真实消费者**：无消费者直接删，不降级保留

## 9. 子任务拆分依据

| 子任务 | 为什么这样拆 |
| - | - |
| A. entity schema 精简 | 独立，无依赖，机械操作 |
| B. 导演/brief 移除 + timeline 建立 | 紧耦合——移除 brief 后 researcher 找素材失去依据，必须同时建 timeline；不能分两次做 |
| C. 游玩设定步 | 玩家流程独立步骤，验证点明确 |
| D. 正式玩家回合 | 核心步骤，storyteller/researcher 职责大改 |
| E. 回合后维护 + frontier 触发 | 前端边界检查和回合后流程紧耦合 |
