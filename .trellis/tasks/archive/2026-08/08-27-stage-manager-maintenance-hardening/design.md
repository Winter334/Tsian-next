# 技术设计：场记回合后维护稳定性优化

## 边界

本任务只改 `cards/沉浸阅读器.tsian-card/` 内会被打包分发的内容。`apps/platform-web/src/storage/workspace-templates/` 已不再维护，不修改、不同步。

目标不是让场记一次拿到更多资料，也不是把每一次多目标维护做成全局原子事务；目标是让 Agent 在需要时能快速定位正确实体，以小而明确的目标批次写入，并根据逐项结果只修复真正失败的部分。

## 提示词与 Skill

`agent.json` 移除 `docs/novel-airp-schema-guide.md` 和 `save/schema/current.md` 的常驻注入。前者含有“无证据也估算属性”的世界建模指令，会诱导场记越过事实维护边界；后者应按字段问题定向读取，而不是每次随调用注入。

`AGENT.md` 缩减为稳定职责和边界：场记只记录当前回合已发生且可证实的状态变化；未知不补猜；不推进 frontier；遇到正式 post-turn 任务先加载 `回合后维护` Skill。正式调用 prompt 只给目标回合和加载 Skill 的指令，不重复流程、schema 或工具细节。

`回合后维护/SKILL.md` 是实际执行规范，使用固定步骤：

1. 加载 Skill，以原生读取取得目标回合正文和 runtime；仅在需要时读取当前 scene、frontier、memory 等已知文件。
2. 将候选信息分为已发生事实、当前明确状态、已表达意图，以及命令、预测、担忧、选项等非事实；后者不得写成 history、status、timeline 或既成关系。
3. 对正文涉及且需要维护的人物/场景/物品，先用实体查询定位，再读取选中实体及所需关联；不从目录或大聚合上下文盲目探索。
4. 已有实体更新；不存在的实体仅在具备跨回合价值时最小创建。原创和原著角色采用同一规则；明显一次性龙套不创建。已知字段可渐进填写，未知字段省略。`attributes` 只能由已有境界、稳定表现和主体事实派生，不能反向制造主体事实。
5. 仅在重要实体确有补齐必要、且已有明确章节或角色定位时，定向读取最小范围源文或参考资料。字段/schema/render 不确定时才读取对应参考段；这不是常规预加载，也不得据此读取未读章节或预测剧情。
6. 按独立目标提交实体、场景、runtime、关系、timeline 等结构化修改；同一目标的相互依赖修改放在同一微批次。
7. 读取每次写入的逐项结果：保留 `applied`/`noop`，只针对可修正的失败目标重新读取并修正一次；不重放成功项。完成核心记录后再维护 memory/seeds，最后写 turn recall。
8. 最终摘要必须反映真实结果：全部必要目标完成才说“维护完成”；必要目标仍未解决时说明“部分维护完成”并列出目标和原因。

恢复规则保持简短：参数形状、版本冲突、可定位的字段或格式问题可重试一次；事实不足、身份不确定、schema 无法表示，或同一目标第二次失败时停止该目标并报告。基础设施读取/写入故障终止当前调用；普通业务操作失败不应中断其他独立目标。

## 实体查询与读取

废弃 `read_maintenance_context` 作为场记的正常入口，也不把它改造成更大的聚合器。回合正文、runtime、memory、frontier 等路径已知的资料由原生读取即可；专用工具只解决原生文件工具效率较差的实体导航问题。

新增 `query_entities`，只返回受限的候选索引与命中理由。它支持精确 ref、类型、名称/别名、lifecycle、场景在场、关系对象或关系类型等过滤，可返回一个或一组目标。查询必须有合理数量上限，并明确区分无匹配与读取失败；它不返回完整实体正文，也不扫描并注入整库。

新增 `read_entities`，接收明确 refs 或查询结果，按请求字段返回实体。可选展开出边、入边或双向关联，并可限制关系类型、`depth`（0 至 2）和 `maxEntities`。返回去重实体、关系边、缺失 refs、单实体读取错误及截断信息，使“未找到”“读取失败”“因上限未展开”不被混淆。

这两个工具不负责 schema 或原著参考文档读取，也不在 Agent 未请求时扩展目标范围。

## 编辑与错误结果

不新增重复实现所有文件编辑能力的“万能实体编辑器”。保留并改造 `json_edit`，因为它相对原生编辑仍有明确价值：实体 ref 定位、结构化的 `set`/`append`/`upsert`/`remove`/`create`/`delete`、ID 与路径约束、保留未知字段，以及一致的操作结果。

`json_edit` 支持自然的外层 `{ target, ops: [...] }`：没有显式 target 的子操作继承外层 target；子操作明确指定冲突 target 或存在无法归一化的混合形状时返回该输入错误。单操作和现有每项显式 target 的批量形式继续兼容。

执行单位是“目标微批次”，不是整个请求事务：

- 同一 target 的操作先在同一快照上规范化、预演和校验；若其中一项无效，该 target 不写入半套字段。
- 目标微批次通过后一次写入该 target。
- 一个 target 失败不回滚其他已成功的 target，也不阻塞其他独立 target 的继续执行。
- 不承诺跨文件事务或全局回滚。

工具应返回完整结构化结果，而不是只有笼统 `status`：每一操作或因前序依赖未执行的操作应标记 `applied`、`noop`、`failed` 或 `not_run`，同时给出 target、操作序号、错误码/简短原因、`retryable` 和最小修正线索。运行时基础设施异常仍可抛错；可预期的输入、版本或数据错误应作为逐项结果返回，方便 Agent 继续维护其他目标。

`text_edit` 不必重造原生 Markdown 编辑。若继续用于 `records.md` 与 `seeds.md`，仅保留这些高频维护文件的轻量格式、序号、重复和状态转换校验，并采用同样的逐目标结果语义；其他文本继续使用现有通用能力。

## 提交顺序与兼容

核心结构化修改先完成，memory/seeds 随后维护，`commit_turn_recall` 始终最后调用。它只负责 recall 写入和本轮最终结果依据，不增加 `maintenanceId`、前端完成门禁或 UI 状态改造：目前没有样本证明“Agent 调用 resolved 被前端误判为同步成功”是实际故障，避免为假设问题扩大改动面。

旧的有效工具调用、旧存档和既有公开结构保持兼容。`read_maintenance_context` 可保留为旧调用兼容或其他 Agent 的工具，但从场记 Tool 列表、Skill 和调用提示中移除；是否最终删除由使用点搜索决定，不能在没有确认调用方的情况下贸然破坏。

## 验证取舍

验证重点是确定性的工具契约与打包链路：查询筛选和界限、关联展开、自然 `target + ops`、同目标失败不半写、独立目标持续执行、结果可驱动局部重试，以及产物包含卡内改动。

不构建大型静态“LLM 行为矩阵”来模拟事实判断、实体取舍或提示服从。这些问题主要由提示词与 Skill 约束解决，使用真实请求抽样和人工复核验证更合适。
