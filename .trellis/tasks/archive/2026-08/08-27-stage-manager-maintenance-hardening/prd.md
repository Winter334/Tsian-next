# 场记回合后维护稳定性优化

## Goal

将场记 Agent 的回合后维护改造成由专用 Skill 驱动、事实边界明确、查询/读取/编辑工具语义清晰且失败可恢复的稳定流程。专用工具必须在实体导航和常见维护动作上明显优于原生文件工具，而不是只把多次原生调用拼成一次。

## Background

- 当前回合后调用提示词要求第一步直接调用 `read_maintenance_context`，本次请求中完整的“回合后维护” Skill 未被加载，模型只获得 Skill Index 摘要。
- 场记常驻上下文全量注入 `docs/novel-airp-schema-guide.md`；其中“无剧情佐证时也要估算属性”的建模规则与场记“只维护已发生事实”的职责冲突。
- `read_maintenance_context` 会一次性读取并返回回合正文、runtime、active scene、相关实体/关系、memory、清理候选和 timeline；它减少了调用次数，但没有提供按目标查询、可控展开和实体维护语义。
- `json_edit` / `text_edit` 的单操作与 `ops` 批量形式互斥，但 Skill 缺少批量示例，脚本也不兼容顶层 `target` 加子操作的自然调用形式。
- `json_edit` / `text_edit` 的批量操作按顺序执行，失败时返回已经完成的结果和失败位置；当前 Skill 没有规定如何消费这些结果、只重试失败项并结束残留的 partial 状态。
- memory 文本只有提示词格式约束，`text_edit` 不校验 records/seeds 的结构、序号或重复内容。
- 实际分发来源是卡内 workspace 文件，并由游戏卡打包脚本产出；平台 workspace template 已停止维护，不是本任务的同步目标。

## Requirements

### R1 — Skill 驱动的固定维护流程

- “回合后维护” Skill 必须成为正式 post-turn 调用的实际执行规范，而不只是可见索引中的可选知识。
- Skill 使用明确、固定、可检查的步骤指导 Agent：加载 Skill、读取目标回合与当前 runtime、查询/读取相关实体、判定事实、补齐必要上下文、执行核心写入、消费逐项结果、维护 memory/recall、输出结果。
- Skill 简要定义异常策略：可修正的参数、冲突或并发问题允许有限重试；单个目标失败时继续完成相互独立目标并记录结果；事实不足、目标身份不确定、schema 不支持或同一目标重复失败时停止该目标并在最终结果中明确报告。
- Skill 明确区分已发生事实、当前明确状态、已表达意图、命令/预测/担忧/即将发生内容，禁止将非事实内容升级为已完成事实。
- Skill 明确 `brief`、`status`、`goals`、`history`、relationship note、memory、seed 和 timeline anchor 的职责边界。

### R1.1 — 渐进实体建模

- 场记遵循“有则更新、无则按需补建”：正文首次出现且确有后续价值的原著或原创角色，都允许创建最小实体；不要求交由世界架构师代建。
- 是否创建由持续价值决定，而非只看是否在正文出现。具名且会持续参与剧情、关系、目标、物品归属、场景在场状态、长期状态或未来召回的角色应创建；明确一次性、无持续交互、可自然弃用的龙套不创建实体。
- 新建或更新时只填写已有证据支持的字段。已知身份、年龄、所属、境界、外观、当前状态、经历或目标可分别填写；未知字段保持缺失，不用模板完整度驱动猜测。
- `attributes` 是依赖角色主体已知境界、剧情表现和稳定描述的派生信息，不能反过来推断主体设定或覆盖正文事实。证据不足时不填；主体事实变化或可用证据补足后再更新。
- 为补齐实体所必需、且已有明确角色或章节定位的角色事实，场记可进行有针对性的源文/参考读取；该读取可覆盖当前 source window 之外的内容，但必须限制到最小可验证范围，不能把未读原著章节当作普通维护资料，也不得为了填满实体进行广泛检索。

### R2 — 按需参考文档与精简提示词

- 场记不再默认全量注入包含世界建模与属性估算规则的通用 schema 指南。
- 常驻提示词只保留角色职责、不变量、Skill 路由和禁止事项；具体流程、工具示例和异常策略由 Skill 承载。
- 为场记提供最小必要的维护字段参考，或明确在遇到字段/schema/render 不确定时按需读取指定参考文档或 call 世界架构师。
- post-turn 调用提示词只负责指定目标回合并启动正确 Skill，不重复维护细节，不引用运行时不存在或已经改名的工具名称。

### R3 — 面向实体的专用查询与读取

- 不再把一个大聚合工具作为场记的唯一入口。回合正文、runtime、frontier、memory 等已知文件由原生 `read` 或窄职责工具读取；实体导航由专用查询/读取工具负责。
- `query_entities` 支持按 ref、类型、名称/别名、生命周期、场景在场、关系目标/类型和有限文本条件筛选一个或多个实体，只返回紧凑索引与匹配原因，不返回全库正文。
- `read_entities` 接受明确 ref 或查询结果，按字段选择返回实体；关联实体可配置方向、关系类型、展开深度和数量上限，返回去重后的展开图和截断信息。未命中、存在但未展开、读取失败必须区分。
- 查询和读取均有边界，不自动扫描整个实体目录，不把 schema 文档或未请求的参考资料注入模型。

### R4 — 面向常见维护动作的专用编辑

- 只有在语义上明显优于原生 `edit` 的地方才新增/保留专用编辑：以实体 ref 定位文件、按字段和数组项执行 update/add/remove、显式 create/delete、保留未知字段、检查实体 id/路径和并发版本，并返回每个动作的结果。
- 不用专用编辑工具重做任意 Markdown/大文件文本替换；普通文本仍使用原生 `edit` 或现有 `text_edit`。
- `json_edit` / `text_edit` 的批量结果必须逐项报告 `applied`、`failed`、`not_run`，包含操作索引、目标和可修正原因；已成功的动作视为已提交，后续循环只处理失败或未执行项，不重复整批。
- 可修正参数、定位冲突和乐观并发冲突由 Skill 指示有限重试；基础设施异常才中止整个调用。不得为了消灭所有 partial 状态而引入跨文件回滚。
- records/seeds 若继续使用专用编辑，只做格式、序号、重复和状态转换的轻量校验；校验失败只影响对应操作。

### R5 — 可恢复的维护交互循环

- Skill 规定每次批量编辑后读取并消费逐项结果：记录已应用动作，修正并重试失败动作，跳过 `not_run` 动作，避免重复已成功写入。
- 若失败动作不是本轮维护的必要项，允许带警告结束；必要项在有限重试后仍失败时，报告“部分维护完成”及未完成目标，不得笼统写成全部完成。
- `commit_turn_recall` 保持最后一步，但不新增未经证实的前端完成标记或同步门禁；它的成功/失败只作为 Agent 最终摘要依据。

### R6 — Timeline 与事实质量

- “显著事件”不能单独触发 player anchor；只有存在足够 source 结果证据时才能判断 `aligned` / `diverged` / `rejoined`。
- source 结果不可比较时只维护 `plotOrder`，不得猜测 alignment。
- memory 与关系导航保持简洁，避免同一事件在同一维护域重复展开成多份剧情历史。

### R7 — 卡内来源与兼容性

- 只修改 `cards/沉浸阅读器.tsian-card/` 内实际参与游戏卡分发的 Agent、Skill、工具、参考文档和调用入口。
- 通过现有游戏卡打包流程验证相关文件被正确纳入分发产物。
- 修改不得破坏现有有效存档格式、已有 Agent 配置和正常 post-turn 调用。
- 为旧工具调用形态提供合理兼容或清晰迁移行为。

### R8 — 低成本验证

- 验证工具 schema、查询/读取的边界与展开参数、批量编辑逐项结果和失败项重试所需信息。
- 不建立大规模静态测试来模拟 LLM 的事实判断、实体取舍或提示遵循；这些通过 Skill、真实请求抽样和打包前人工检查验证。

## Acceptance Criteria

- [ ] 正式 post-turn 调用实际加载并遵循“回合后维护” Skill；Skill 先读取目标回合和当前 runtime，再按需要查询/读取实体。
- [ ] 场记默认上下文不再包含要求无证据估算属性的通用建模指令。
- [ ] 查询工具能够找到正文相关但不在 active scene 的既有角色，并明确区分不存在与未展开。
- [ ] 读取工具能够按目标一次展开实体及可配置深度的关联实体，且有数量边界。
- [ ] 专用编辑仅覆盖比原生 `edit` 更有价值的实体语义动作；无法拉开差距的通用文本编辑不重复实现。
- [ ] 顶层 `target + ops` 等可明确归一化的调用不会产生协议形状错误；不可归一化输入返回真实失败。
- [ ] 批量编辑逐项返回 applied/failed/not_run；成功动作不被重试，失败动作可单独修正和重试。
- [ ] 不会把预测、命令或即将发生的行动写成已完成事实，也不会无依据补充当前伤势、NPC goals 或 timeline alignment。
- [ ] 首次出现且需要跨回合保留的原创或原著角色能按已知事实创建最小实体；一次性龙套不会被无差别建模。
- [ ] 新实体及后续更新只写已有证据支持的字段；未知境界不生成属性，属性不会反向制造角色主体事实。
- [ ] records/seeds 非法格式、错误序号和可识别重复内容会被拒绝。
- [ ] turn recall 按 Skill 规定作为最后一步提交；失败摘要能指出未完成目标，不引入额外前端门禁。
- [ ] 游戏卡打包结果包含更新后的场记 Agent、Skill、工具、参考文档和调用入口。
- [ ] 仅运行低成本工具烟测、构建和卡内分发清单检查；不要求维护或同步已停止维护的平台 workspace template。

## Out of Scope

- 重写 storyteller 的正文生成逻辑。
- 重构整个 Novel AIRP schema 或所有 Agent 的参考文档体系。
- 修改或同步已停止维护的 `apps/platform-web/src/storage/workspace-templates/` 平台模板。
- 通过更换模型或单纯调整 temperature 规避结构性问题。
- 将 frontier 推进职责转移给场记，或改变 frontier 的剧情推进业务规则。

## Resolved Decisions

- 场记可以直接创建首次出现但确有跨回合维护价值的原著或原创角色；不依赖世界架构师预建。
- 实体按“有则更新、无则按需补建”维护。具名且持续参与剧情、关系、目标、物品、场景、长期状态或未来召回的角色应建模；明确一次性、短暂退场且无持续价值的龙套不建模。
- 实体字段采用渐进填充：已知即写，未知即省略；不为满足模板完整度猜测身份、境界、状态、目标或其他主体事实。
- `attributes` 是由主体已知事实、境界和稳定剧情表现推导出的衍生信息，不能反向制造或覆盖主体事实。证据不足时不填，主体变化或证据补足时再更新。
- 在当前维护证据不足、但确有实体维护必要且已有明确定位时，允许场记定向读取当前 source window 外的最小范围源文补齐。该能力不能用于预测后续剧情、批量读取未读章节或填满档案字段。
