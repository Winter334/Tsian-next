# 文本工具协议重试与历史标签混淆治理

## Goal

提高 Text Tool Protocol 在普通聊天模型上的工具调用成功率，使模型即使连续产生不同类型的协议格式错误，也能在有界成本内恢复；同时保持历史工具记录绝不被当作新调用执行，避免重复写入或其他副作用。

## Background

- 2026-08-17 的真实开局建模测试中，模型在 `agent_call` 成功后首次生成 `commit_opening` 时返回无效 JSON，运行时给出一次协议重试；重试响应的调用参数已基本完整，但外层使用了历史标签 `<tsian-tool-call-records>`，最终以 `TEXT_TOOL_PROTOCOL_NON_EXECUTABLE_TAG` 耗尽重试。
- 同一测试更早一轮已经发生过一次相同的历史标签回显，并在当时的一次重试中恢复，说明这是可重复的模型混淆模式，不是单次偶发解析异常。
- 当前系统提示既包含多个历史工具记录，也展示了完整的 `<tsian-tool-call-records>`“错误示例”；成功工具轮还会持续把该结构作为 assistant 历史回放。可执行标签 `<tsian-tool-calls>` 与历史标签只相差词尾，模型可见形态高度相似。
- 当前协议只允许一次连续格式重试。任意一次合法工具调用后预算会重置，但 `INVALID_JSON` 后紧接历史标签回显会直接失败。
- 解析器拒绝历史标签是安全边界。历史标签不能自动降级为可执行调用，否则可能重放已经执行过的写操作。
- 本次失败发生在工具执行前；`commit_opening` 未执行，运行时事务按现有契约丢弃了本回合暂存写入。
- 当前模型侧工具交互历史由两条关联消息组成：assistant `<tsian-tool-call-records>` 保存调用 id、名称和参数，user `<tsian-tool-observations>` 保存同 id 的成功/失败及 result/error。它们是当前工具循环的精确执行转录，不是跨会话永久历史。
- 跨回合只持久化受限的语义 `toolMemories` 投影；原始调用参数、原始 observation 和文本协议消息不会作为模型历史持久化。
- 当前 task 模式压缩先在代码侧定位尾部工具交互段，再按完整工具轮分组；保留最近 5 轮原文并固定保留尚未被后续成功调用解决的失败轮，其余早期消息连同旧摘要一次性发送给压缩模型，产出一条 user checkpoint。调用与 observation 并不会分开发送给压缩模型，role 只是当前分组器使用的结构信号之一。

## Key Decisions

- 已执行调用及其 observation 改为 runtime 注入的单条 user 执行报告，不再以 assistant 消息回放；执行报告使用清晰的非执行标签和调用 id 表达边界。
- 文本 task 压缩按标签和 id 分组，不依赖 assistant/user 角色差异；最近轮次与未解决失败轮的保留语义不变。
- 连续协议错误允许最多 3 次纠错模型调用，即初始响应后最多再尝试 3 次；任一合法工具调用后预算重置。
- 纠错提示按错误代码给出正向、可执行的修正动作，只展示正确协议模板，不展示完整错误示例或自动执行宽松修复结果。

## Requirements

- R1. 新工具调用必须继续只接受唯一、明确的可执行协议格式；任何模型回显的历史、观察或协议错误载荷都不得直接执行。
- R2. 模型可见的协议提示与工具历史回放应降低“历史记录”和“待执行调用”的结构相似度，不再用完整负例强化错误输出模式。
- R3. 协议错误恢复必须是有界的：初始响应后最多允许 3 次连续纠错模型调用；合法工具调用后预算重置，不能形成无限循环。
- R4. 无效 JSON 不得通过可能改变参数语义的宽松解析或猜测修复后直接执行；写操作参数必须经过严格 JSON 解析。
- R5. 针对无效 JSON、历史标签回显、标签未闭合/多块、非数组/空数组、调用项/名称/参数无效等错误返回简短、直接、只展示正确目标格式的专用纠错提示；最终正文不得泄漏协议标签或工具载荷。
- R6. 合法工具调用只能执行一次。增加恢复能力不得造成重复调用、重复写入或历史调用重放。
- R7. 保持原生工具调用模式、共享工具 schema、工具执行器、事务回滚和现有权限边界不变。
- R8. 文本协议任务压缩与工具名提取仍能识别调整后的历史交互表示。
- R9. 为解析器、提示构造和连续错误恢复链路提供自动化回归覆盖。
- R10. 当前工具循环需要保留可核验的执行转录：调用 id、工具名、严格解析后的参数，以及同 id 的 accepted observation；多工具并行调用不得失去对应关系。
- R11. 原始执行转录只服务于当前工具循环和本轮任务压缩；跨回合继续只保留现有受限语义工具记忆，不新增原始工具协议持久化。
- R12. 文本协议执行转录必须由 runtime 以 user 角色注入；模型产生的 assistant 响应中只有 `<tsian-tool-calls>` 可以表示新的待执行调用。
- R13. 文本 task 压缩必须按执行报告标签和调用 id 识别完整工具轮，不以 assistant 角色作为文本协议调用历史的必要条件；最近轮次保留和未解决失败轮固定保留语义不得改变。
- R14. 任务收尾必须审计本次触及的测试文件，删除或合并只覆盖单次实现细节、与更广泛契约测试重复的专项回归；保留公共契约、安全/数据损失边界和无法被更通用测试替代的必要回归，并将该判断规则写入质量规范。

## Acceptance Criteria

- [ ] AC1. 新鲜模型响应中的历史/观察/错误标签始终返回协议错误，且不会触发工具执行。
- [ ] AC2. 模型依次返回无效 JSON、历史格式、未闭合块，第四次返回合法调用时，运行时成功恢复，并且目标工具恰好执行一次。
- [ ] AC3. 初始响应及其后 3 次纠错响应均无效时，以包含最后协议错误代码的明确错误终止，不发起第五次协议尝试，不返回空正文或伪成功。
- [ ] AC4. 文本协议系统提示只提供完整的正确调用示例，不再包含可被直接模仿的完整错误调用块。
- [ ] AC5. 工具历史表示与 `<tsian-tool-calls>` 在命名或结构上有清晰区分，同时保留调用 id、名称、参数与 observation 的关联信息。
- [ ] AC6. 严格 JSON 校验保持不变；不存在自动补引号、自动转义或容错 JSON 后直接执行写工具的路径。
- [ ] AC7. 既有文本工具交互压缩、工具名提取和上下文预算行为在新历史表示下通过回归验证。
- [ ] AC8. 原生工具调用模式行为不变；`apps/platform-web` 要求的构建与相关自动化测试通过。
- [ ] AC9. 当前循环的执行转录能完整关联每个调用及其 accepted observation；正式 turn/context 持久化中不出现原始调用参数或 observation。
- [ ] AC10. Provider-bound 消息中，已执行调用及其 observation 只出现在 runtime user 消息中，不存在 assistant `<tsian-tool-call-records>` 历史。
- [ ] AC11. 单条 user 执行报告在 task 压缩中计为一个完整工具轮；默认最近 5 轮原文保留、未解决失败轮固定保留及早期 checkpoint 摘要行为与修改前等价。
- [ ] AC12. 每类协议错误的纠错消息都包含当前错误代码、明确的剩余纠错次数、对应修正动作，以及唯一正确的 `<tsian-tool-calls>` 模板或“无工具时正常作答”的出口。
- [ ] AC13. `assistant-runtime.smoke.test.ts` 中本次新增/修改的断言经过保留价值审计：重复或过度绑定提示文案细节的专项断言被合并/删除，长期协议、安全、压缩和回滚契约仍有清晰覆盖；质量规范包含每次任务收尾执行该审计的规则。

## Out of Scope

- 自动把模型配置从文本协议切换到原生工具调用。
- 把 `<tsian-tool-call-records>` 兼容为可执行调用格式。
- 为无效 JSON 引入 JSON5、通用 JSON repair 或其他语义不确定的自动修复。
- 修改 `commit_opening` 的业务 schema、开局建模 Skill 或工具执行权限。
- 与本协议失败无关的前端 UI 重设计。
