# 沉浸式 HTML-in-Canvas 平台 UI

## Goal

为 Tsian 新增一套独立的沉浸式平台 UI 方案，使平台能够在保留真实 HTML 布局、内容与交互能力的同时，使用 Canvas、WebGL 或 WebGPU 实现传统 DOM UI 难以实现的动态视觉效果，并允许该方案采用与现有 UI 不同的整体布局。

该方案不直接替换现有 UI；它与现有 UI 并存，并在后续迭代中逐个适配既有功能面板。

## Background and Confirmed Decisions

- 用户目标不是为现有 UI 更换颜色或样式，而是获得液态扭曲、辉光、粒子、溶解、像素化、动态模糊、3D 透视、空间化界面和镜头转场等更强的视觉表现。
- 新方案对外可以表现为可选择的“主题”，但必须能够替换平台布局与渲染方式，而不只是修改设计令牌或 CSS。
- 现有 UI 继续作为稳定方案保留；新 UI 独立演进。
- 开发过程可以按面板逐个实现和验证，但新 UI 不会在部分适配状态下上线。
- 新 UI 达到约定的完整功能范围后才发布；未适配面板不嵌入新 UI，也不通过兼容容器临时承载。
- HTML-in-Canvas 当前属于实验性 Web 平台能力，浏览器覆盖和规范稳定性不足以支持无回退的全量替换。
- 用户接受在 HTML-in-Canvas 仍需浏览器实验 Flag 时发布新 UI，不要求等待 API 在所有目标浏览器中默认启用。
- RetroOS 与 Spatial Desktop 被视为两套独立工作环境；切换 UI 时允许重新加载平台并重新初始化桌面会话。
- Spatial Desktop 首版仅面向具备鼠标或触控板、WebGL、HTML-in-Canvas 实验能力和足够视口空间的桌面 Chromium 环境；窄屏与手机继续使用 RetroOS。

## Repository Evidence

- `apps/platform-web/src/App.vue` 当前直接挂载 `DesktopShell`，平台尚不存在可切换的 UI 方案或主题选择机制。
- 当前 RetroOS 外壳由 `components/desktop/DesktopShell.vue`、`DesktopWindow.vue` 和 `composables/useDesktopWindows.ts` 共同实现，布局与窗口行为不是单纯 CSS 主题。
- `apps/platform-web/src/desktop-apps.ts` 已将平台应用的路由、标题、图标、内容组件和窗口元数据集中注册；新 UI 可以复用这些功能视图与路由身份，而不复制平台业务逻辑。
- 现有约定明确区分“平台外壳拥有应用/窗口框架”与“路由视图拥有领域内容”，这为替换外壳、逐步适配内容提供了现成边界。
- 当前 `style.css` 将 RetroOS 设计令牌、全局基础样式、桌面外壳样式和内容级 `retro-*` 样式集中在同一文件；新 UI 不能仅通过覆盖少量 CSS 变量获得独立布局。
- 既有窗口必须在最小化或失焦时保留渲染树，避免滚动位置、表单草稿和运行时状态丢失；任何新 UI 兼容承载既有视图时也必须尊重这一行为约束。
- 控制面板此前已为未来“桌面主题”类别预留产品位置，但尚未创建真实主题功能。

## Visual Direction

- 新 UI 的核心风格确定为 **Spatial FUI / Immersive Sci-Fi HUD（空间化未来界面 / 沉浸式科幻 HUD）**，与旧 UI 的 RetroOS 形成鲜明区分。
- 参考视觉使用深黑蓝空间、蓝青主光、少量橙色告警色、极细结构线、微型信息排版、模块化数据块、点阵/网格、低强度辉光与轻微 RGB 色散或故障感。
- 整体界面应具有独立面板悬浮在空间中的弯折、遮挡与包围感，而不是把普通平面网页套进圆角玻璃卡片，也不是把所有窗口粘到同一张全屏曲面幕布上。
- 曲面形态确定为**逐窗局部浅弧面 + 2.5D pose 合成**：环境保持稳定，每个窗口独立拥有局部曲率、深度、朝向、尺度和层级。中央窗口近正视，侧区窗口克制后退并朝向视点。
- 窗口曲率只改变所属 Source；移动、缩放或改变一个窗口的 pose 不得扭曲其他窗口、启动器、状态区或背景。V1 不引入可导航完整 3D 世界，而以逐窗可逆投影满足准确交互。
- 活动主界面保持可感知但克制的局部曲率，不要求交互时完全展平；正文、表单和关键操作必须可读。
- 窗口视觉基线采用灰白实体无边框主体，不使用网格、渐变、纹理、选中阴影或外发光。标题/拖拽入口与最小化/关闭分别放在常驻左右顶部突出块中，使用炭灰和少量环境红色强调，不恢复完整横向标题栏。
- 曲面屏外应保留环境空间与可选的侧向信息面，用于建立虚拟座舱/VR 空间感，而不是让曲面内容贴满浏览器视口后失去空间参照。
- 新 UI 的产品形态确定为 **Spatial Desktop（空间桌面）**：空间场景承载多个独立平台应用窗口，不是单应用展示屏。
- 侧向空间允许打开和操作完整的次级功能窗口，不限制为状态、导航或静态预览；多个应用可以独立悬浮、遮挡并同时存在。
- 窗口在曲面桌面中拥有稳定的空间位置。聚焦窗口只改变活动状态、层级和路由，不自动旋转、平移或重定位桌面；用户实测确认自动聚焦移动会破坏空间定位感。
- 窗口远近应属于未来摄像机 zoom，而不是改变单个窗口尺寸。摄像机滚轮拉近/拉远暂缓；本阶段滚轮保持普通内容滚动语义。
- 默认 Spatial 窗口应以可读的大尺寸打开，目标约为常见 1920×1080 视口的 58% 宽、72% 高，再受各应用最小值和可恢复视口边界约束；窗口尺寸仍只通过边缘拖动调整。
- 窗口继续支持自由拖动与缩放，不采用强制网格或固定插槽布局。
- 窗口接近侧区时应产生克制的 pose 变化，使其方向、尺度和深度自然面向视点；用户仍可再次拖动改变位置，聚焦本身不得改变 pose。
- 鼠标、触控或可用的姿态输入应驱动克制的空间视差：背景、环境标记、面板与前景高光处于不同深度层。
- 曲面、视差和故障效果必须服务于层级与状态表达；活动内容应保持清晰可读，不能让所有正文和表单持续处于强畸变或色散中。
- 动效应支持降低或关闭运动强度，避免眩晕并尊重 `prefers-reduced-motion`。

## Requirements

- 新 UI 方案必须能够定义独立于现有 UI 的页面布局、导航位置、内容区域、面板组织和交互表现。
- 新 UI 必须延续平台的多窗口桌面心智，支持多个平台应用同时打开，并在曲面空间中完成聚焦、切换、移动、调整尺寸、最小化和关闭。
- 曲面吸附不得破坏自由窗口操作；拖动、缩放和吸附结果必须稳定、可预测，并能在视口尺寸变化后恢复到可操作区域。
- 新 UI 方案必须支持将真实 HTML 内容与 Canvas、WebGL 或 WebGPU 视觉效果组合使用。
- 新旧 UI 必须能够并存，用户或平台能够选择使用哪套 UI 方案。
- UI 模式切换只保留持久化业务数据和当前路由，不要求迁移已打开窗口、窗口位置、尺寸、层级、最小化状态等桌面会话信息。
- 既有业务状态、用户操作和平台数据不得因增加新 UI 而形成两套互不兼容的业务实现。
- 新 UI 必须允许功能面板按批次逐步适配；尚未适配的功能不能阻塞现有 UI 的继续使用。
- 新 UI 在达到发布范围前必须保持为本地开发能力，不向正式用户暴露半成品入口。
- 新 UI 不得嵌入现有 RetroOS 面板作为临时兼容方案，也不得在操作过程中自动切换到旧 UI。
- 在 HTML-in-Canvas 不可用的环境中，平台必须保持可用，并提供明确、稳定的回退行为。
- 在窄屏、手机、缺少 WebGL 或其他不满足 Spatial Desktop 首版条件的环境中，不要求提供曲面桌面的等价降级实现，用户继续使用 RetroOS。
- HTML-in-Canvas 不可用时的告知机制暂不作为当前设计阻塞项：可以使用运行时能力检测与界面内引导，也可以先通过平台公告说明浏览器与 Flag 要求；具体机制在实现前按当时 API 状态确认。
- 新 UI 的交互内容应保留键盘操作、可访问语义与正常文本排版能力，不能为了视觉效果退化成纯位图界面。
- 新 UI 必须支持空间深度层、曲面屏视觉形变以及输入驱动视差，并为活动内容提供稳定、清晰的阅读与操作状态。
- 曲面区域内的指针命中、悬停、拖动与滚动必须与视觉位置一致，不能出现越靠近屏幕边缘偏差越大的交互问题。
- 特效强度必须可分层控制；正文、表单和高频操作不得长期承受影响辨识或命中精度的强故障、色散或弯折。

## Initial Scope

- 建立一套可选择的沉浸式 UI 方案及其布局边界。
- 建立 HTML 与 Canvas/GPU 效果组合的基础能力。
- 内部首个可验证切片确定为“Spatial Desktop 基础外壳 + 我的应用”：它同时覆盖曲面多窗口、路由、卡片网格、图片、快捷操作、上下文菜单和真实 DOM 命中，但不单独上线。
- 定义后续功能面板逐步实现、独立验证以及最终整体验收的接入规则。
- 明确新 UI 首次发布必须覆盖的完整功能面板清单。

## First Release Functional Parity

根据当前平台应用注册与全局宿主结构，首次发布按“全部平台自有 UI 完成适配”理解：

- 平台外壳、导航、应用入口与全局状态区域。
- 创意工坊、我的应用、应用属性。
- 资源管理器、工作区编辑器、媒体查看器。
- 工作室、桌面助手。
- 控制面板、账号中心、公告中心、系统监视器。
- 游戏启动与 Play 宿主界面；游戏卡自行提供的 iframe 前端内容保持独立，不纳入平台 UI 重写。
- 启动画面、Toast、确认框、通用浮窗等平台级全局交互。

内部实现仍按可独立验证的子阶段推进，但以上范围全部通过整体验收前，新 UI 不发布。

## Out of Scope

- 第一阶段直接替换或删除现有 UI。
- 为尚未实现 HTML-in-Canvas 的浏览器复制一套等价的底层渲染引擎。
- 在新 UI 中嵌入旧 RetroOS 面板或提供自动切回旧 UI 的临时兼容路径。
- 将部分完成的新 UI 提前暴露给正式用户。
- 完整 3D 世界、可导航摄像机、6DoF、深度物理、手动 Z 轴拖动、景深模糊和 XR 控制器；V1 使用逐窗 2.5D 合成。

## Acceptance Criteria

- [x] 平台可在现有 UI 与新沉浸式 UI 之间选择，切换不会改变业务数据。
- [x] 切换 UI 后平台在当前路由对应的应用中重新打开；旧桌面的窗口会话不会被错误映射到新桌面。
- [x] 新 UI 可以采用与现有 UI 明显不同的整体布局，而不受现有组件树结构限制。
- [x] 首次发布范围内的全部功能面板均已在新 UI 中完成适配，不依赖旧 RetroOS 面板或自动切换回旧 UI。
- [x] 新 UI 展示真实 HTML 交互与 Canvas/GPU 动态效果的组合价值，而不是仅更换色板或 CSS 装饰。
- [x] 新 UI 在视觉上形成可辨识的 Spatial FUI 风格，包含独立窗口曲面、至少三个可感知深度层和输入驱动视差。
- [x] 用户可以在空间桌面上同时看到并操作多个独立平台应用窗口，次级窗口不只是装饰性预览。
- [x] 聚焦任意窗口不会自动移动桌面或改变任何窗口的空间位置，只更新活动状态、层级和路由。
- [x] 窗口默认以接近常见视口 58% 宽、72% 高的阅读尺寸打开，正文无需额外缩放即可清晰辨认；窗口尺寸仍由边缘拖动调整。
- [x] 滚轮不会改变单个窗口尺寸；摄像机拉近/拉远留待后续单独设计。
- [x] 环境不经过统一全屏曲面；每个窗口具有独立、可逆且克制的局部弧面，移动一个窗口不会改变其他 Source 的轮廓。
- [x] 中央大窗口、侧后方窗口和下层窗口通过清晰遮挡、尺度与朝向形成层次，不呈现为一张透明橡胶幕布；窗口不依赖选中阴影、外发光或装饰边框建立层级。
- [x] 默认窗口使用灰白无纹理实体主体和常驻左右顶部突出块；增强后的局部曲面在 1114×778 默认窗口上形成约 28–34px 中央 bow，同时文字与控件保持平滑可读。
- [x] 窗口可自由拖动与缩放；进入侧向区域时自然后退并朝向视点，且不会被不可逆地锁进固定布局。
- [x] 活动面板中的正文、表单与关键操作保持清晰可读；关闭或降低运动效果后，所有功能仍可完成。
- [x] 不支持 HTML-in-Canvas 的浏览器仍能使用现有 UI，且不会进入损坏或不可操作的中间状态。
- [x] 发布时用户能够获知所需浏览器/Flag 条件；采用自动检测还是平台公告可按当时 API 状态决定。
- [x] 不满足桌面端视口、输入设备或图形能力条件时，平台不会进入残缺的 Spatial Desktop，而是继续提供完整 RetroOS。
- [x] 新 UI 中已适配的交互内容可使用键盘操作，并保留合理的可访问语义。
- [x] 后续面板适配具有明确的接入边界，不需要复制业务状态或核心操作逻辑。
