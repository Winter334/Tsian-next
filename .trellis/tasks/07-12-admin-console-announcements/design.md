# Admin console and announcements — Design

Planning artifact for `.trellis/tasks/07-12-admin-console-announcements/`.

## Design Goals

- Keep the admin UI separate from the normal player platform bundle.
- Put all admin authority in backend checks, not frontend routing or hidden buttons.
- Optimize admin UX for readable lists, clear state, and low-risk operations.
- Keep announcements simple: title/body/time/history/read locally.
- Use heartbeat-based presence instead of realtime sockets.

## Package / App Boundaries

```text
apps/admin-web/              # new separate Vue/Vite admin app
apps/platform-web/           # existing player desktop, announcement center + presence taskbar only
apps/platform-server/        # admin auth, admin APIs, public announcement/presence APIs
packages/contracts/          # shared response/request shapes
```

`apps/admin-web` must not import UI/components from `apps/platform-web`. It can share `@tsian/contracts` types and can duplicate small, app-local API helpers/styles where that keeps the admin bundle independent.

Root workspace/build updates:

- add `apps/admin-web` to `package.json` workspaces;
- add root script such as `build:admin`;
- keep `build:web` building only the player platform.

## Backend Architecture

### Config

Extend `apps/platform-server/internal/config/config.go`:

```go
type Config struct {
    // existing fields...
    AdminDiscordIDs []string
    AdminStaticDir  string
}
```

Environment variables:

- `TSIAN_ADMIN_DISCORD_IDS`: comma-separated Discord user IDs that are admins.
- `TSIAN_ADMIN_STATIC_DIR`: default `../admin-web/dist`.

The allowlist is server-only. Do not expose configured Discord IDs through public APIs.

### Admin authorization

Add a backend admin gate:

```text
RequireAuth -> Discord identity allowlist check -> next
```

Implementation options:

- Add `middleware.RequireAdmin(cfg, db, users, next)` and share as much auth lookup logic with `RequireAuth` as practical.
- Admin check queries `auth_identities` for the current user:

```sql
SELECT 1
FROM auth_identities
WHERE user_id = ? AND provider = 'discord' AND subject IN (...allowlist...)
LIMIT 1
```

HTTP semantics:

- missing/invalid session: `401`;
- valid session but not admin: `403`;
- valid admin: request continues with user in context.

Admin probe endpoint:

```http
GET /api/v1/admin/me
```

Response:

```ts
interface AdminMeResponse {
  user: User
  isAdmin: true
}
```

### Static serving

Serve admin static assets separately from the platform SPA:

```text
/admin/* -> adminSpaHandler(AdminStaticDir, stripPrefix="/admin")
/*        -> existing platform spaHandler(StaticDir)
```

`/api/*` remains API-only and must not fall through to either SPA.

`apps/admin-web/vite.config.ts` should use `base: "/admin/"` for production asset paths.

## Database Changes

The existing migration style is `CREATE TABLE IF NOT EXISTS` plus additive column checks in `apps/platform-server/internal/storage/db.go`.

### Workshop visibility

Add columns to `market_packages`:

```sql
hidden_at TEXT
hidden_by TEXT
```

No full moderation/audit system is introduced. `hidden_by` stores the admin user ID that last hid the resource; unhide clears both fields.

Rules:

- `hidden_at IS NULL` = public/visible;
- `hidden_at IS NOT NULL` = hidden from ordinary Creative Workshop flows;
- admin list/detail can include both.

### Announcements

Add table:

```sql
CREATE TABLE IF NOT EXISTS announcements (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
)
```

Index:

```sql
CREATE INDEX IF NOT EXISTS idx_announcements_created ON announcements(created_at DESC)
```

There is no lifecycle/status/expiry/severity table in MVP. Deleting an announcement physically removes it.

### Presence sessions

Add table:

```sql
CREATE TABLE IF NOT EXISTS presence_sessions (
  id TEXT PRIMARY KEY,
  user_id TEXT,
  last_seen_at TEXT NOT NULL,
  created_at TEXT NOT NULL
)
```

Indexes:

```sql
CREATE INDEX IF NOT EXISTS idx_presence_sessions_last_seen ON presence_sessions(last_seen_at)
CREATE INDEX IF NOT EXISTS idx_presence_sessions_user ON presence_sessions(user_id)
```

`id` is a cookie-backed browser-session ID generated by the server. `user_id` is nullable and updated when the heartbeat request is authenticated.

### Presence package

Create:

```text
apps/platform-server/internal/presence/presence.go
apps/platform-server/internal/presence/sqlite_repo.go
apps/platform-server/internal/presence/handler.go
```

Endpoints:

```http
POST /api/v1/presence/heartbeat
GET  /api/v1/presence/summary
```

Response:

```ts
interface PresenceSummaryResponse {
  onlineCount: number
  activeWindowSeconds: number
}
```

Cookie:

- name: `tsian_presence`;
- generated when absent/invalid;
- `HttpOnly`, `SameSite=Lax`, `Secure` follows `CookieSecure`;
- long-lived enough for a browser session/profile, e.g. 30 days.

Semantics:

- heartbeat upserts `presence_sessions(id, user_id, last_seen_at, created_at)`;
- summary counts `last_seen_at >= now - 60s`;
- heartbeat may delete rows older than a longer retention window (e.g. 10 minutes) opportunistically.

### Market admin handlers

Keep admin market handlers in the `market` package so they can reuse package response helpers and blob cleanup behavior without exposing internals across packages:

```text
apps/platform-server/internal/market/admin_handler.go
```

Endpoints:

```http
GET    /api/v1/admin/market/packages
GET    /api/v1/admin/market/packages/{id}
PATCH  /api/v1/admin/market/packages/{id}
POST   /api/v1/admin/market/packages/{id}/hide
POST   /api/v1/admin/market/packages/{id}/unhide
DELETE /api/v1/admin/market/packages/{id}
```

List query parameters:

- `resourceType` — existing resource type filter;
- `q` — search name/summary/resource id where practical;
- `tag` — optional existing tag filter;
- `visibility` — `all | visible | hidden`, default `all` for admin;
- `uploader` — optional fuzzy uploader display/ID search if practical;
- `limit`, `cursor`, `sort` — reuse existing pagination/sort where possible.

Admin metadata update uses JSON, not multipart package replacement:

```ts
interface AdminMarketPackageUpdateRequest {
  name: string
  summary: string
  tags: string[]
}
```

Do not allow admins to replace another uploader's package bytes in MVP.

Public market behavior changes:

- ordinary list/count exclude hidden rows;
- ordinary get/download/cover/cover-thumb return `404` for hidden resources;
- ordinary owner routes also remain ordinary platform flows and should not surface hidden resources unless a later product decision says uploaders can see hidden moderation state.

## Admin Web UX Design

### App shell

Use a direct management layout, not a desktop/window metaphor:

```text
┌─────────────────────────────────────────────────────┐
│ TSIAN ADMIN                  admin user / logout     │
├──────────────┬──────────────────────────────────────┤
│ Overview     │ current module content                │
│ Workshop     │                                      │
│ Announcements│                                      │
└──────────────┴──────────────────────────────────────┘
```

States:

- loading session;
- unauthenticated: show login button/link to existing `/api/v1/auth/login`;
- forbidden: clear no-access message;
- authorized: admin shell.

### Workshop page

UX priorities:

- list-first;
- scan states without opening details;
- low-risk action hierarchy.

Layout:

- top filter row: search, resource type, visibility, uploader if implemented, refresh;
- table rows: type, name, uploader, downloads, visibility, created/updated, actions;
- detail side panel or inline detail region for selected resource;
- edit metadata form in detail;
- hide/unhide as normal management action;
- permanent delete only in a separated danger zone with confirmation.

Avoid placing permanent delete as a one-click row action.

### Announcements page

UX priorities:

- simple list;
- simple editor;
- clear feedback.

Layout:

- list of announcements ordered newest first;
- create button;
- editor form with title + Markdown body;
- live or explicit preview using the same safe announcement Markdown renderer as the player announcement center;
- save/create/delete actions;
- delete requires confirmation.

No rich text editor, scheduling, draft flow, severity picker, or expiry controls.

On initial announcement fetch, do not toast every historical unread announcement. After initial load, if polling/refresh discovers a newly created announcement ID, show one non-blocking toast and update the taskbar unread count.

## Markdown Rendering

Announcements use Markdown source for readability, but Markdown rendering must be safe and consistent across `apps/admin-web` preview and the player announcement center.

Existing evidence:

- `apps/platform-web` already has `apps/platform-web/src/lib/markdown.ts`, using `marked`, `marked-highlight`, and a small Highlight.js language set.
- That renderer is assistant-chat oriented and currently returns raw marked HTML for `v-html`; announcement rendering should not rely on unsanitized raw HTML because announcement content is stored server-side and displayed to all players.

Create an announcement-specific safe renderer in both frontend apps, or in a shared browser-safe package only if that does not couple `admin-web` to `platform-web` internals.

Required Markdown support:

- paragraphs and line breaks;
- headings;
- emphasis/strong;
- ordered/unordered lists;
- blockquotes;
- links;
- tables;
- inline code;
- fenced code blocks with highlighting where dependencies are already available.

Safety requirements:

- Disable or sanitize raw HTML in Markdown output.
- Remove script/style/iframe/object/embed and event-handler attributes.
- Reject or strip dangerous URL schemes such as `javascript:` and `data:` from links.
- Prefer opening external links with `target="_blank" rel="noreferrer noopener"`; internal links may remain normal.
- Use one renderer path for admin preview and player display so preview matches published output.

Implementation options:

1. Add a small sanitizer dependency such as DOMPurify to `apps/platform-web` and `apps/admin-web`, then render with `marked` + sanitize the resulting HTML.
2. If avoiding a new dependency, implement a conservative renderer/custom marked renderer that escapes raw HTML and only emits known-safe tags/attributes. This is more error-prone and should only be chosen if dependency policy blocks DOMPurify.

Recommended: DOMPurify + marked, because good Markdown UX with tables/code/links and safe `v-html` is otherwise easy to get subtly wrong.

## API Data Flow

### Admin access

```text
admin-web mount
  -> GET /api/v1/admin/me
      401 -> login state
      403 -> forbidden state
      200 -> render admin shell
```

### Workshop hide

```text
admin clicks hide
  -> POST /api/v1/admin/market/packages/{id}/hide
  -> db: set hidden_at, hidden_by
  -> admin list row shows hidden
  -> public market list/get/download excludes package
```

### Announcements

```text
admin-web creates announcement
  -> POST /api/v1/admin/announcements
  -> db announcements row
platform-web polls/list announcements
  -> GET /api/v1/announcements
  -> taskbar unread count + announcement center list
```

### Presence

```text
platform-web mounted
  -> POST /api/v1/presence/heartbeat every ~30s
      server sets tsian_presence cookie if needed
      server upserts last_seen_at
      response includes onlineCount
  -> DesktopShell displays onlineCount
```

## Validation Strategy

Backend tests:

- admin me: unauthenticated `401`, non-admin `403`, allowlisted Discord ID `200`;
- admin market hide/unhide: admin can change state, public endpoints 404 hidden rows, admin endpoints still see hidden rows;
- admin metadata update: updates name/summary/tags only, does not require package bytes;
- admin delete: removes DB row and package blobs as existing owner delete does;
- announcements: public list, admin create/update/delete, validation errors;
- presence: heartbeat sets/uses presence cookie, summary counts only recent sessions.

Frontend checks:

- `npm run build:contracts` after contract changes;
- `npm run build:web` after platform taskbar/announcement changes;
- `npm run build:admin` for new admin app.

Go checks:

- `go test ./...` under `apps/platform-server`.

## Trade-offs

- Separate `apps/admin-web` increases setup/build work but keeps admin UI out of the normal player platform bundle.
- Heartbeat presence is approximate but avoids socket infrastructure and is enough for a taskbar online count.
- Local announcement read state is not cross-device, but avoids user-read tables and keeps the announcement MVP simple.
- `hidden_at` is a minimal moderation state, not a full governance workflow; this matches the MVP scope and keeps deletion as a rare dangerous action.
