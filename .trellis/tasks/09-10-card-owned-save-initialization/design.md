# 初始存档归属与承载方案

## 已核实的生产链（2026-09-10）

| 内容 | 实际权威来源/消费者 | 分发/生效方式 |
| --- | --- | --- |
| 卡 manifest、提示词、Skill、工具脚本、静态文档 | `cards/沉浸阅读器.tsian-card/card-manifest.json` 与 `workspace/` | 整卡打包、导入/上传/分发 |
| 卡游玩前端与维护调用文案 | `apps/play-frontend-dev/src/` | 打包脚本读取并编译进卡包；不能以卡目录 frontend/src 副本判断最新行为 |
| 新存档初始资料 | `storage/saves.ts:createLocalSaveFromGameCard` → `storage/workspace.ts:createDefaultSaveRuntimeFiles` → `storage/workspace-templates/files.ts:DEFAULT_SAVE_RUNTIME_FILES` | 当前由平台源码生成，与卡业务 schema 耦合 |
| 缺省文件补齐 | `storage/workspace.ts:upgradeDefaultWorkspaceFilesForSave` + `DEFAULT_SAVE_RUNTIME_UPGRADE_FILE_PATHS` | 打开/升级路径可能补入旧模板，不能只改新建存档入口 |
| 开局中的动态业务资料 | 卡内世界架构师 Skill/脚本（如 `_opening-workflow.js`、`commit-opening-state.js`） | 动态生成但生成代码随卡分发，不意味着一定要改平台 |
| 旧内置 Agent/Skill 能力模板 | `storage/workspace-templates/agents/` 等 | 已非沉浸阅读器维护/分发源；但仍有内置卡或测试引用，需要先追踪再删 |

当前 packager 的 `frontendRoot` 是 `apps/play-frontend-dev/src`；workspace 收集明确拒绝 `save`、`.tsian`、`frontend` 保留根。`storage/game-cards.ts` 同样拒绝卡内容直接占用 `save/` 和 `.tsian/`。因此初始资料不能简单塞入 `workspace/save/`，需要独立的卡资产命名空间与显式映射。

当前 `GameCardRuntimeConfig` 只有 entrypoints；归一化函数只重建已知字段，打包脚本也有严格键检查。新配置必须贯穿合同、归一化、包读写，而不是仅修改作者 manifest。

## 已确认的承载方式

**用户确认的方向**：玩法 schema/初始存档应跟随卡；平台最多提供简单通用兜底。

**2026-09-10 用户已认可**：小型声明式配置引用卡内的“初始存档文件树”，文件内容仍使用普通 JSON/Markdown/文本。平台只做受限复制，不理解内容里的角色、属性、场景或玩法 schema。不增加必选初始化脚本。随后用户认可具体合同及取消旧卡隐式初始化，并明确测试阶段无需兼容/迁移建设。

最终目录布局（已实现）：

```text
card-manifest.json       # 声明某个卡资源目录为初始存档来源
workspace/
  initial-save/           # 本卡选用的目录名，独立于活动 save/
    playthrough/runtime.json
    schema/current.md
    memory/records.md
    memory/seeds.md
  agents/
  tools/
```

平台将声明目录的相对路径实例化为新存档 `save/...`；卡原始资产不被修改。卡作者可以使用完全不同的目录/内容，不以沉浸阅读器的示例树为平台标准。声明负责“复制哪些初始资料”，不是定义另一个系统级 schema DSL。

## 为什么当前不推荐脚本作为必选入口

现有默认资料主要是静态 JSON/Markdown，可直接搬成卡资产；为复制文件执行脚本会额外引入权限、执行生命周期、超时、失败回滚、重复执行和调试成本。

真正需要随机开局、输入派生或条件计算时，脚本有价值，但应放卡内业务初始化能力，并在存在具体需求时设计受限协议。不要默认在“导入卡”时执行代码，也不以自由文件系统/网络访问作为初始化能力前提。本轮建议先实现声明式静态模板，不预建无人使用的脚本钩子。

## schema、模板、开局生成不是同一件事

- schema/字段语义/渲染规则：卡的定义与工具/前端合同；可在游玩中由世界架构师参与演进。
- 初始模板：新存档的起始文件和值，可以只是待填写的最小骨架，不必提前知道导入小说的世界观。
- 开局生成：结合玩家输入/小说/选择生产实际资料，由卡内已有 Agent/脚本继续完成。

平台知道如何实例化模板，不知道模板代表什么世界。这样 schema 后续被重写，也不需要平台重新理解它。

## 兜底与失败边界（已确认）

1. 未声明初始模板：使用最小通用环境，平台内部 metadata 独立创建；业务 `save/` 文件可为空。不能继续默认塞入 AIRP roster、小说 source/frontier、六维属性等。
2. 不新增显式空模板模式：无需初始业务文件时省略配置；声明目录没有任何文件时报告配置错误。
3. 声明了模板但路径/文件/合同错误：在校验或创建时报告，不静默降级为通用模板。
4. 新建时实例化一次，数据与初始 checkpoint 一致。初始化失败不能留下可见半成品。
5. 卡升级影响后续新建存档，不自动覆盖既有存档。本项目测试阶段不实现旧卡兼容或迁移层；官方卡随本任务更新。
6. 平台只校验路径、媒体/文件约束和合同，不校验某玩法的 JSON 字段。文件目标受限于业务 save 范围，不允许访问 `.tsian` 或越界。

## 清理顺序

A. 列出活跃默认文件及生产/消费/升级引用，确认内置空白卡和测试依赖。
B. 按已确认声明协议与最小兜底补齐合同及包往返，不增加旧卡分支。
C. 将 AIRP 初始资料搬至卡资产，接入新建存档和必要开局准备；保留平台内置 metadata。
D. 关闭会重新灌入 AIRP 的通用默认/升级路径，调整真实消费者与测试。
E. 移除已无消费者的旧能力模板或陈旧副本，避免将清理扩大成兼容框架。
F. 以真实卡包导入与两类不同卡验证，再进入主任务。

## 2026-09-10 定稿：最简单的初始化合同

用户认可上一轮提议，并明确“项目还处于测试阶段，只有沉浸阅读器一张官方卡；兼容和迁移几乎都不需要，保持最简单逻辑”。这是当前任务的范围约束，不是宣称系统永远不允许未来出现迁移需求。

1. 配置：`runtime.initialSave: { templateRoot: "initial-save" }`。路径相对卡工作区虚拟根；不含 `workspace/`。不增加 kind/version/script/merge 等选项。
2. 复制：声明根下文件相对路径映射到新存档 `save/`，内容原样复制，无宏展开、无业务 schema 解释、无 AIRP 默认混合。平台 `.tsian` 独立创建。
3. 兜底：未声明则业务文件为空，只有平台必要记录/内部元数据/初始 checkpoint；不能假装通用兜底可满足任意卡的私有 schema。
4. 空目录：现有包以文件条目承载数据，空目录不能可靠表达。因此取消前期“显式合法空模板”的候选设计；不需要初始业务文件就省略配置，声明根却无文件则报错。
5. 旧卡：无模板配置与普通无配置卡同等处理，不保留隐式 AIRP 初始化、不检测卡名或历史版本分配特殊默认文件。官方沉浸阅读器同步搬入初始资料、声明配置并更新包。
6. 旧存档：不按模板补写/覆盖/删除业务资料，不建立迁移框架或版本链。移除平台自动回灌 AIRP 默认文件的路径；不自动清空用户测试数据。
7. 生命周期：导入仅校验/保存，创建时实例化一次；卡升级只影响之后的新存档；重开与回溯不执行初始化。
8. 校验仍需保留真实边界：路径安全、资源存在、配置往返、平台元数据隔离、初始文件与 checkpoint 一致。简单逻辑不等于静默接受坏包或牺牲数据安全。

### 此次明确不做

旧卡专用兼容分支、自动存档迁移、模板版本合并、双轨初始化、升级时补业务文件、空模板模式、初始化脚本钩子、宏/变量模板语言。不同 schema 隔离使用最小测试夹具验证，不因此新增第二张官方卡。
